# Known limits

Accepted trade-offs of the current backend. Each has an owner step.

| Limit | Behaviour | Planned fix |
| --- | --- | --- |
| Redis-down rate limiter | If Redis is unreachable the limiter lets requests through and logs `rate_limiter_unavailable`. Logins stay available but are unthrottled. | Kept on purpose. |
| Register reveals emails | `POST /auth/register` returns 409 `email_taken` for an existing email, so registered addresses can be probed (limited to 5 registrations per IP per hour). | Kept on purpose. |
| Proxy IP and rate limits | `X-Forwarded-For` is ignored; limits use the direct peer IP. Behind a reverse proxy all users share one IP and per-IP limits (30 logins/min, 5 registers/hour, 30 refreshes/min) apply to everyone. | Step 14/15 (security, deployment): trusted-proxy handling. |
| Simultaneous refresh race | Two requests refreshing with the same cookie at once: the second sees a revoked token and revokes the user's whole token family, logging them out everywhere. | Step 11 (frontend): add a short grace window for the just-rotated token. |
| Type inference on uploads | Types come from the first ~1 MB of a CSV (first 10,000 rows of an Excel sheet). If a later value does not fit, the file is re-read and each column is promoted on its own (integer to decimal, then boolean, date, timestamp). Only a column that cannot be parsed becomes text, and the version gets one warning per such column; if even that fails, the whole file is stored as text as a last resort. Columns whose name has an identifier token (`id`, `code`, `number`, `no`, `num`, `phone`, `zip`, `sku`, and Arabic `رقم`/`كود`/`هاتف`/`جوال`) and columns with leading-zero values (`00123`) stay text. A column that is not named like an identifier loses leading zeros only if they first appear after the sampled first 1 MB / 20,000 rows of a CSV that never needed the re-read. Excel dates come back as timestamps. | Step 3 fixed identifiers; per-column type overrides are not built yet. |
| Upload size check happens after spooling | Starlette spools the multipart body to a temp file before our streaming check enforces `MAX_UPLOAD_MB`, so an oversized request still costs temp disk and bandwidth before the 413. | Step 15 (deployment): reverse-proxy `client_max_body_size`. |
| Excel is read as values | `.xlsx` is read with `data_only=True`: formulas show their last cached value (empty if the file was never opened in Excel), merged cells keep the value only in the top-left cell, one sheet per version. | Kept on purpose; upload one version per sheet. |
| Soft delete keeps files | `DELETE /datasets/{id}` hides the dataset and blocks queries but keeps the original and Parquet files on disk. | Step 14 (security): retention and purge job. |
| Query layer has no HTTP route yet | `SafeQueryService` is used by preview and (later) the analysis engine and agent; there is no public SQL endpoint. Each query loads the Parquet into memory (`QUERY_MEMORY_MB`, default 512 MB; 256 MB in compose), so very wide files near the 2,000,000-row limit can hit that cap and fail with a clear error. | Step 8: exposed only through the agent's `run_sql` and `make_chart` tools (1000 rows, 10 s), not as a public route. |
| Encoding sniffed from the first 1 MB | Invalid bytes only after the first 1 MB of a non-UTF-8 file surface as a parse error instead of switching encoding. | Not fixed in Step 3 (kept documented); revisit if users hit it. |
| Profile memory | Profiling and cleaning run in the worker over a DuckDB view of the Parquet file with `PROFILE_MEMORY_MB` (512 MB; 256 MB in compose) and no spilling to disk. A very wide or very large file can exceed it; the profile then ends `failed` (the dataset stays usable) and the rerun button will fail again until the limit is raised. Cleaning uses window functions (impute, outlier flags) that need the whole column in memory. | Step 15 (deployment): size the worker. |
| Duplicate rows are hash-based | Exact duplicates are found by a 64-bit hash of the whole row, so a collision (about 1 in 10^10 for 2 million rows) would hide one duplicate. The dedupe fix itself groups on the real values. | Kept on purpose. |
| Quality score weights are calibrated on fixtures | The 30/25/15/15/15 split is fixed, but penalty factors (for example 6x the average null rate) were tuned so the generated clean twin scores 100 and the messy twin about 57. Treat scores as relative (before/after, dataset vs dataset), not absolute. | Revisit with real customer data. |
| Percent text becomes a fraction | `15%` and `١٥٪` are read as 0.15 when a text column is cast to numbers. | Kept on purpose. |
| Ambiguous dd/mm dates | When no value proves the order (all numbers up to 12), the cleaning plan assumes day-first, marks the fix `high` risk and never recommends it; the user picks `dayfirst` or `monthfirst`. | Kept on purpose. |
| Role refinement with a real provider is untested live | `LLM_PROVIDER=deepseek` sends masked samples of weak columns through `complete_json` (JSON mode, thinking off); with `fake` the scripted model keeps the rule-based roles. No live call was made in Step 8 (no account balance). | Run the live tests once the account has a balance. |
| Analysis loads role columns into memory | Each run loads only the role-mapped columns of the version into a DuckDB table limited by `ANALYSIS_MEMORY_MB` (512 MB; 256 MB in compose) with no spilling; a file near the 2,000,000-row limit with many role columns can exceed it and the run fails with a friendly error. | Step 15 (deployment): size the worker. |
| Evidence SQL runs on typed role columns | Insight SQL runs on the typed role columns (text dates and amounts are converted first). On a file whose dates or amounts are stored as text, the stored SQL returns different rows through `SafeQueryService` until the cleaning plan has been applied. | Step 8: the agent re-types columns. |
| Currency and locale come from run config | Currency is not detected. Insight text shows no currency unless `currency` is set (with `locale`) in the run config, and a re-run inherits the last run's settings. Insight text is English with locale-formatted numbers only. | A later step feeds currency and locale from the company profile; Step 8/10 (LLM polish, reports). |
| Seasonality needs history | STL needs 24 months; 12-23 months use a plain monthly average (low confidence); under 12 months no seasonality insight. Weekday pattern needs 4+ weeks of daily data. | Kept on purpose. |
| Earlier runs lose their insights | A re-run (or auto-run) replaces the version's insights, so older runs of the same version keep their status but list no insights. | Kept on purpose. |
| Role overrides do not re-run the analysis | Changing a column's role (`PUT /datasets/{id}/columns/{name}/role`) does not queue an analysis, so existing insights keep the old roles until `POST /datasets/{id}/analyze` is called. | Step 11 (frontend prompts a re-run). |
| MLflow has no authentication | The MLflow server accepts anyone who can reach port 5000 and forecast runs are logged to it (tagged per tenant). Compose publishes it on 127.0.0.1 only. It must not be exposed beyond localhost until it is locked down. | Step 14/15 (auth proxy or MLflow auth, network policy). |
| Forecasts ignore holidays, Ramadan/Eid, promotions and external data | Only the history of the series is used, so moving festivals are smeared over neighbouring months and one-off campaigns look like noise. | A later modelling step, once calendars and event data exist. |
| Forecast needs history | Under two full seasonal cycles only simple models run and confidence is low; with exactly two cycles a trend is usually not learned reliably (the baseline often wins and is reported as such); three cycles are needed for high confidence. | Kept on purpose: prefer "not enough data". |
| Group forecasts are independent | The category forecasts are not reconciled with the total, so they need not add up to it. | A later step if reports need it. |
| Forecast memory is measured on the whole process | FORECAST_MEMORY_MB compares the worker's total RSS, which already includes the loaded libraries; a worker that starts above the limit forecasts the total with the baseline only and says so. | Tune from docker stats in Step 15. |
| Anomaly precision depends on volume | At around 7 orders a day, single large orders make ordinary days look extreme; on the planted 2-year files precision is 0.57-0.71 and about 0.5 on 3-year files (fixed 1% alert budget). Weekly and monthly data use a simpler rolling-median baseline. | Revisit with real customer data; tune the alert budget per tenant. |
| Level shifts need 65 weeks of daily data | Year-over-year ratios need a year of history before the shift can be measured; shorter histories get a warning and no level-shift check. | Kept on purpose. |
| Row-level forest sees a sample | The Isolation Forest that ranks extreme prices trains on `ANOMALY_ROW_SAMPLE` rows (plus the rule candidates); counts always use every row. Row numbers refer to the stored data of the version, not necessarily the original upload. | Kept on purpose. |
| Customer ids are stored | Per-customer segment assignments (customer id, or a pseudonym when the id column is personal data) are kept in Postgres with the run, replaced on re-run, and deleted only with the tenant. | Step 14 (security): retention and purge with the dataset. |
| PSEUDONYM_SECRET must be set in production | When it is empty the HMAC key is derived from JWT_SECRET (a warning is logged at startup), so rotating JWT_SECRET changes every customer pseudonym. Set PSEUDONYM_SECRET separately and keep it stable. | Step 15 (deployment): require it in production. |
| Segments describe, they do not explain | RFM segments and K-Means groups summarise past behaviour; K-Means always returns 3-8 groups, and recommended actions are rule-based suggestions, not tested interventions. | Step 7 added drivers; they are associations too (see below). |
| Churn is "no purchase in the next W days" | Churn is a lapse of W days (twice the typical customer's median gap, 30-180 days), not a cancellation. Slow but loyal buyers can be labelled churned, and the model is checked on one later window only, so its AUC has sampling noise of a few points. Customers inactive for a year are left out of the risk list (they already lapsed). | Revisit with real customer data; a subscription-style `churn_flag` replaces the label. |
| Churn flag has no date | With a `churn_flag` column the label comes from the flag, the check is 5-fold cross-validation (no later period), days since the last purchase and the spend trend are left out (they may describe behaviour after leaving), and confidence is capped at medium. | Kept on purpose. |
| Churn probabilities are clipped | Calibrated risks are kept within 0.5%-99.5%; isotonic calibration on a few hundred churners is coarse (steps), so treat probabilities as bands, not exact values. Per-customer reasons come from SHAP on the uncalibrated model (log-odds). | Kept on purpose. |
| Churn scores are stored per customer | `churn_scores` holds one row per active customer (id, or a pseudonym when the id column is personal data), replaced on re-run and deleted only with the tenant. | Step 14 (security): retention and purge with the dataset. |
| Drivers are associations | Revenue drivers come from a model of revenue per line; they show which factors go together with revenue, not what causes it. Price is part of how revenue is calculated, so it ranks high mechanically. Correlated factors (price and category) share SHAP credit. Confidence is never above medium. Factors with a permutation R² drop under 0.005 on later lines are listed as "no clear link". | Kept on purpose; causal claims need experiments. |
| Elasticity is observational | Price elasticity is a log-log regression on past weekly sales. If prices were set in response to demand (raised when busy), the estimate is biased; weeks with no sales cannot be logged and are dropped, which biases sparse items towards zero. Estimates that are positive, above 5 in size or whose 95% interval includes zero are never used. On the planted files the category estimate is within 0.3 of the truth in 29 of 30 files and its interval holds the truth in 29 of 30. | A later step: promotion calendars and price-test data. |
| Analysis worker memory with Step 7 | Measured during full runs (every module, 3-year files of 13,000-47,000 rows): peak 473 MiB on `--anomalies --segments`, 492 MiB with `--elasticity --drivers` added and 486 MiB on the churn walkthrough file, of the worker's 768m limit; sampled about every 2 s with `docker stats`, so a short spike can be missed. SHAP runs on every scored customer without sampling at these sizes. | Step 15: re-measure on real customer files. |
| What-if is synchronous and annual | `POST /datasets/{id}/what-if` runs in the API process on the same memory-limited DuckDB table as an analysis run (one aggregation and a small regression per scope, about a second); at most `WHATIF_MAX_CONCURRENT` (2) run at once per API process, others wait up to 20 s and then get 409 `what_if_busy`. Results are yearly changes against the last 12 complete months; the baseline band uses month-to-month variation, which includes seasonality, so it is wide for seasonal businesses. Fallback from product to category to all items is a small specification search; the scope used is always shown. | Move to the worker if datasets grow; Step 10 (reports) shows ranges. |
| What-if text has no currency | Amounts in what-if summaries are plain numbers rounded to 3 significant figures (exact values in the JSON). | Step 10/11 (reports, frontend) format them with the company currency. |
| First forecast in a fresh container is slower | numba compiles the statistical models on first use (cached under NUMBA_CACHE_DIR, which lives inside the container). | Step 15: warm the cache when the worker starts. |
| Parallel tests are opt-in | `make test` runs serially on one database. `make test TEST_WORKERS=N` runs pytest-xdist with one database (`analyst_test_gwN`), storage folder and MLflow store per worker, then a serial pass for tests marked `@pytest.mark.serial` (none today: repeated 2-, 4- and 8-worker runs showed no test that needs it), and merges coverage before the gates. Each worker peaks at about 600-700 MB. CI picks its worker count from the runner's CPUs and memory. Docs-only changes (`docs/**`, `*.md`) skip the CI job; this is safe only while the `backend` check is not a required status check. | Revisit the worker count when the suite or the runner changes. |
| Number verifier proves presence, not meaning | The verifier shows that every number in an answer appears in that turn's tool results (allowing rounding, k/M/B, percent/fraction and Arabic-Indic digits; integers up to 12 and numbers from the question are exempt). It does not prove the number is used for the right quantity: a correct revenue figure could be called profit. That is why evidence is always shown and the Step 9 evaluation checks answers against ground truth. | Step 9 (evaluation suite). |
| No real model tested yet | All Step 8 tests and the walkthrough use `LLM_PROVIDER=fake` (scripted test model or scripted doubles); the DeepSeek client is tested only against a mocked HTTP transport. Answer quality, tool choice, Arabic replies and real token costs are unmeasured. | Run `pytest -m live_llm` once the DeepSeek account has a balance; Step 9 measures answers. |
| Costs are approximate | Per-million prices default to approximate DeepSeek peak rates (deepseek-flash input 0.44 / cached 0.014 / output 1.32 USD; deepseek-v4-pro 1.32 / 0.044 / 3.96) and must be checked against https://api-docs.deepseek.com/quick_start/pricing. Off-peak discounts are not modelled; every cost in events, messages and the API is labelled approximate. | Update the `LLM_PRICE_*` settings when prices change. |
| Scripted analyst covers few questions | `LLM_PROVIDER=fake` answers only net revenue, forecast, anomalies, segments, churn, price what-ifs, "what should I do", top products and `run python:` blocks (English plus a few Arabic keywords); anything else gets a clarifying question. It is a test model and says so in every answer; it refuses to start with `APP_ENV=production`. | Kept on purpose (tests and demos only). |
| Sandbox shares a uid with its server | User code runs in a child process under the same uid as the sandbox's HTTP server. If every in-process layer (static check, restricted builtins, audit hook, rlimits) were bypassed, the code could tamper with the socket while its own job runs. It still has no network (`network_mode: none`), no storage volume and only the requesting tenant's columns. | Step 14: run jobs under a second uid or gVisor. |
| Sandbox runs one job at a time | `SANDBOX_CONCURRENCY` is 1: a second `run_python` call while one runs waits up to 2 s, then the tool reports "sandbox busy". Jobs get 400 MB address space and 15 s inside a 512 MB / 1 CPU container. | Scale the sandbox service when usage grows. |
| Sandbox gets role columns as CSV | Only role columns are sent (personal-data columns dropped, a personal-data customer id pseudonymised, unless the company opted in). Above `SANDBOX_MAX_UPLOAD_MB` (20) a seeded random sample is sent and the result says so; sample totals are not dataset totals. Types travel as a small dtype map (no pyarrow in the sandbox). | Kept on purpose. |
| Personal data in SQL is column-based | `run_sql` judges the parsed sqlglot tree, not the SQL text: any reference to a personal-data column is blocked (every alias, quoting, case, comment, subquery and CTE spelling), and so is anything that names no column (`*`, `t.*`, `#1`, `COLUMNS(...)`, a table or alias used as a value), except plain `COUNT(col)`/`COUNT(DISTINCT col)`. `PIVOT` is refused because it turns row values into column names, and result column names over 128 characters are refused. Values derived from such a column through other columns (for example an id that encodes an email) are not detected. Opt-in is all-or-nothing per company. | Step 14 (security review). |
| Injection scanner is a heuristic | Instruction-like text in tool output (English and Arabic phrases, `import os`, `/etc/passwd`, ...) only adds a caveat; the real defences are the delimiters, the system-prompt rule, tool-argument validation, tenant-bound tools and the sandbox. A real model can still be misled into a wrong but harmless answer. | Step 9 adds injection cases to the evaluation. |
| Agent runs in the api process | Each stream runs the synchronous agent loop in the api's thread pool (sync SQLAlchemy). Per user: 20 questions per minute and 2 open streams (slots expire after 10 minutes if a disconnect skips cleanup). Forecast jobs started by the agent are polled for up to 60 s. | Move the loop to a worker if answers get long. |
| Daily budget counts reservations | Before each model call an estimate (prompt plus `LLM_MAX_OUTPUT_TOKENS`) is reserved; it is settled to the real usage afterwards, so a tenant close to the budget can be refused a call that would actually have fit. Budgets reset at midnight UTC. | Kept on purpose (never overspends). |
| Conversation summaries are lossy | After `AGENT_SUMMARY_AFTER` messages, messages older than the last `AGENT_HISTORY_MESSAGES` are folded into a short summary by the cheap model; their numbers are not evidence for later answers. | Kept on purpose (no vector store in Step 8). |
